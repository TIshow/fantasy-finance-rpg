# AI and Human Development Workflow

最終更新：2026-10-29

## 1. 目的

Codex、Claude Code、人間のエンジニアが、セッションや担当者が変わっても、同じ前提、決定、現在地から作業を再開できるようにします。

会話履歴や各AIの自動メモリは補助情報です。プロジェクトの正本はGit管理された文書とコードです。

## 2. 情報の階層

| 層 | ファイル | 役割 | 更新頻度 |
| --- | --- | --- | --- |
| 常時指示 | `AGENTS.md` | 全エージェント共通の短いルール | 低い |
| Claude入口 | `CLAUDE.md` | `AGENTS.md`を読み込む薄いラッパー | 非常に低い |
| 現在地 | `docs/STATUS.md` | フェーズ、完了、次、ブロッカー | 作業ごと |
| プロダクト正本 | `docs/PROJECT_CHARTER.md`等 | 要求、ルール、設計 | 変更時 |
| 判断履歴 | `docs/DECISIONS.md` | なぜその判断をしたか | 重要判断時 |
| 変更履歴 | Git commit / Pull Request | 誰が何をどう変えたか | 変更ごと |

重要な背景を`AGENTS.md`へすべて詰め込みません。常に必要なルールだけを置き、詳細は関連文書へのリンクにします。

## 3. 正本ルール

- チャットだけで決まった重要事項は、作業完了前に正本へ記録する
- AIの自動メモリだけにプロジェクト事実を残さない
- 仕様変更と実装変更を同じPull Requestで整合させる
- 文書間で矛盾した場合は、実装で勝手に決めず矛盾を解消する
- 決定を覆す場合は履歴を消さず、置き換えた理由を残す
- 日付、状態、未決事項を明示する

## 4. セッション開始手順

Codex、Claude Code、人間のいずれも、次の順で開始します。

1. リポジトリルートから作業を始める
2. `AGENTS.md`を読む。Claude Codeは`CLAUDE.md`経由で参照する
3. `docs/STATUS.md`を読む
4. `docs/PROJECT_CHARTER.md`と関連仕様を読む
5. `docs/DECISIONS.md`の関連判断を確認する
6. `git status`、現在ブランチ、最近のコミットを確認する
7. 作業範囲と完了条件を短く言い直す
8. 不明点が実装結果を大きく変える場合だけ確認する

## 5. タスクの渡し方

AIへ依頼するときは、最低限次を含めます。

```md
## 目的
何を達成したいか

## スコープ
変更してよい領域／変更しない領域

## 参照
読むべき仕様・決定ID

## 受け入れ条件
完了を確認できる具体的な条件

## 検証
必要なテスト、レビュー、画面確認

## 制約
期限、依存追加、外部変更、互換性、データ安全性
```

「いい感じに作る」ではなく、成果と境界を明示します。実装方法まで不要に固定せず、変更してはいけない契約を明確にします。

## 6. 作業中の原則

- 変更前に既存状態を読む
- 小さく縦に動く単位で作る
- 無関係な変更を混ぜない
- 不確実な点を事実として書かない
- 途中で新しい重要判断が生じたら、`docs/DECISIONS.md`へ記録する
- コードができたら、見た目だけでなく重要な状態と失敗経路を検証する
- 外部サービス、依存、権限、秘密情報を暗黙に増やさない
- 他の担当者の未コミット変更を上書きしない

## 7. セッション終了／引き継ぎ手順

実質的な変更を終えたら、次を行います。

1. 変更内容を確認する
2. 関連する検証を実行する
3. 仕様と実装が一致しているか確認する
4. 重要判断を`docs/DECISIONS.md`へ記録する
5. `docs/STATUS.md`へ完了、検証、未解決、次の一手を記載する
6. 秘密情報と不要な個人情報がないか確認する
7. 焦点を絞ったコミットまたはPull Requestにする
8. 実行できなかった検証を明示する

次の担当者がチャット履歴を読まずに再開できなければ、引き継ぎは未完了です。

## 8. CodexとClaude Codeの役割分担

両者に固定の担当を割り当てる必要はありません。同じ正本と受け入れ条件で作業し、得意な使い方をします。

例：

- 一方が実装し、もう一方が独立レビューする
- 一方が市場計算を検証し、もう一方が子ども向けUXを確認する
- 一方が不具合を再現し、もう一方が修正案を比較する
- 大きな作業はファイル領域を分け、同一ファイルの同時編集を避ける

同じ変更を複数AIに並行実装させて、無計画に混ぜません。並行化するときは、成果物、所有ファイル、統合担当を先に決めます。

## 9. レビューの観点

一般的なレビューに加え、GUILD MARKETでは次を必ず確認します。

- 締切後や一時停止中に注文を受け付けないか
- 二重注文、二重清算、二重精算を防いでいるか
- 清算の結果が注文の到着順やブラウザの時計に左右されないか
- 残高、価格、権限をクライアントだけで決めていないか
- 切断後に正しい状態へ復帰できるか
- シナリオと市場エンジンが密結合していないか
- 一人プレイが参加者数に依存していないか
- NPCを実在プレイヤーに見せかけていないか
- 児童・保護者の不要な個人情報を取得していないか
- AIレポートがレビュー済みシナリオから逸脱しないか
- 教育効果についてデータ以上の主張をしていないか

## 10. 文書の保守

- `AGENTS.md`は短く安定させる
- `CLAUDE.md`は共通指示の重複コピーにしない
- `STATUS.md`は完了した作業の長期アーカイブにせず、現在地を上部に保つ
- 詳細設計は該当する仕様へ置く
- 一時的な調査メモを正本と混同しない
- 文書リンク切れと矛盾をレビューする
- 実装開始後は正式コマンドを`AGENTS.md`と`CONTRIBUTING.md`へ記載する

## 11. セキュリティと外部操作

- GitHubリポジトリは初期段階では非公開
- APIキー、トークン、認証情報をコミットしない
- `.env.example`には値ではなく変数名と説明だけを書く
- 外部への公開、デプロイ、課金、権限変更は、タスクで明示された範囲だけ行う
- 実在参加者データをローカル開発へコピーしない
- AIへ渡すログは仮名化し、必要部分だけにする
- 自動生成物もレビューなしで本番へ反映しない

## 12. 現行公式ガイドとの対応

2026-09-02時点の公式ガイドに基づき、次の構成を採用しています。

- Codexはリポジトリ階層の`AGENTS.md`を永続的なプロジェクト指示として読む
- Claude Codeは`CLAUDE.md`を各セッションで読み、`@AGENTS.md`で共通指示を取り込める
- Claude Codeの`CLAUDE.md`は短く保ち、詳細資料は別文書へ分離する
- Git履歴とPull Requestを人間・AI共通の変更記録にする
