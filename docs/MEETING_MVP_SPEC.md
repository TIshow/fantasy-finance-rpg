# Proposal Meeting MVP Specification

最終更新：2026-10-29
状態：Draft（方針・約定方式・NPC・技術構成はD-024〜D-027でAccepted。時間配分と画面の細部は内部テストで確定）

関連：`MARKET_SPEC.md`（市場の規則）、`ARCHITECTURE.md`（構成、状態機械、同期、データ、API）、`SCENARIO_01.md`（本文と値）、`GAME_DESIGN.md`（ルールと体験）

## 1. 目的

銀行への提案会議で、5〜6人が各自のスマートフォンから同じ人工市場に参加し、約5分の対戦を体験できる状態にします。説明ではなく体験で、GUILD MARKETの面白さを伝えます。伝えたい流れは「ニュースを読む → ほかの商会の動きを予想して注文する → 締切で一斉に公開される → 次の判断を変える」です。

提案会議MVPは使い捨てのデモではありません。銀行イベントMVPへ広げる、同じアプリとゲームエンジンの最初の版です（D-024）。

## 2. 範囲

含むもの：

- QRコードまたは6桁の参加コードと、商会名だけでの参加
- 5ラウンドの自動進行（運営が一時停止、延長、早期締切できる）
- 買う・売る・保有の予約、締切ごとの一斉約定と公開
- 調査券（第3・第4ラウンドのどちらかで1回）
- 決算、順位、最初と最後の本命（D-021）、価格のリプレイ
- 参加者、運営、会場画面の3つの画面
- 本番環境での試合の作成（CLI）と、当日の手順書

含まないもの：

- 30〜50組規模の負荷対策（イベントMVPで扱う）
- 親子向けの文言や進行（第2ラウンドの2面表示は入れる）
- 正式な運営者認証（O-007）
- 計測基盤とアンケート
- 管理画面（試合はCLIで作る）
- 同じ試合の再戦（優先度を下げる。同じシナリオを2回遊ぶと結末が分かるため）
- 生成AI、課金、外部サービスとの連携

## 3. 想定する場

| 項目 | 想定 |
| --- | --- |
| 参加者 | 銀行の担当者など大人5〜6人（定員12商会） |
| 端末 | 各自のスマートフォン（iOS Safari、Android Chrome）。1台＝1商会 |
| 会場画面 | ノートPCからTVまたはプロジェクターへ出す |
| 運営 | 発表者が、同じノートPCか自分のスマートフォンで操作する |
| 回線 | 各自の4G／5G。会場のWi-Fiを前提にしない |

## 4. 対戦の形式

ラウンドの内容は`SCENARIO_01.md` §3のとおりです。

1ラウンドは「ニュース10秒 → 注文受付35秒 → 公開10秒（演出待ち2秒を含む）」の約55秒です。5ラウンドで約4分35秒、決算と順位発表を含めて約5分になります。QRからの参加（ロビー）は別に1〜2分みます。時間はすべてシナリオの設定で変えられます。

流動性の倍率は k=2、1枠の上限は10口を初期値にします（`MARKET_SPEC.md` §5）。

## 5. 画面

### 5.1 参加者（スマートフォン）

- **上部に固定：** 商会名、使える現金と予約中の額、総資産、調査券、ラウンドと残り時間
- **4ギルドのカード（1列）：** 印、名前、価格、前回比（色だけでなく矢印と符号で示す）、保有口数
- **注文：** ギルドを選び、「買う／売る」と口数（1・5・10）を選んで予約します。買いでは「最大○G（余りは約定後に戻ります）」を表示します。売買の操作は画面の下部に置きます。
- **予約の一覧：** 予約中の注文と、その変更・取消
- **受付の外：** ニュース中、公開中、一時停止中は予約できず、理由を表示します。
- **公開：** 全端末で同時に新価格へ切り替えます。表示するものは次の3つです。
  - 自分の結果：約定、一部約定、不成立と、その理由
  - 王国の商会100の動き（例：ドラゴン 売り61・買い9・様子見30）
  - 参加者全体の動き
- **調査券：** 第3・第4ラウンドの注文受付中だけ使えます。3つの情報源から1つを選びます。
- **決算：** 優勝ギルド、最終資産、順位、最初と最後の本命と資金配分（D-021）、価格のリプレイ
- 主要なボタンの高さは44px以上にし、360px幅で主要な操作が隠れないようにします。

### 5.2 運営

- 参加用のQRコードと参加コード、参加中の商会と接続状況（最後に状態を取得した時刻）
- 開始、一時停止、再開、延長、早期締切、次へ（手動モード）、中止
- 現在のフェーズ、残り時間、清算の状態
- 開始、早期締切、中止には確認を出します。運営の操作はすべて記録します。

### 5.3 会場画面

- 4ギルドの価格と推移のチャート、ラウンドと残り時間、ニュース
- 公開の演出：一斉に新価格へ切り替え、注文の内訳を人数で示す
- 順位（商会名と総資産）、決算、リプレイ
- 個別の予約や保有は表示しません。

### 5.4 リプレイ

横軸をラウンド、縦軸を価格とした4本の折れ線を表示します。重ねて表示するものは次のとおりです。

- 人気ニュース、事故映像、AIレポート、公式照合の位置
- 自分が調査券を使った位置
- 自分の注文（参加者の画面のみ）
- NPCの注文のまとまり
- 最初と最後の本命

結果を「当たった／外れた」だけで終わらせず、「どの情報で何を変えたか」を振り返れる構成にします。

## 6. ビジュアル方針

- **雰囲気：** 夜の王国取引所。ゲーム性は高いが、賭博の画面には見せない
- **色：** 背景は深いネイビー、パネルは青みのある濃色、主なアクセントはゴールド。買いはグリーン、売りはレッド、情報はブルー
- **表示：** 上昇・下落は色だけでなく矢印と符号で示す
- **文字と印：** 本文はOS標準の日本語フォントを使う。ギルドの印はインラインSVGで作り、絵文字を主な識別に使わない
- **演出：** 派手な点滅、長い演出、音声の自動再生は使わない

## 7. 受け入れ条件（会議に出してよい条件）

機能

1. 5〜6台のスマートフォン（iOS Safari、Android Chrome）が、QRから30秒以内に商会名だけで参加できる
2. 5ラウンドが自動で約5分で進み、運営が一時停止・延長・早期締切できる
3. 各ラウンドで買う・売る・保有を予約し、締切までは変更・取消できる
4. 締切ごとに参加者と100商会の注文が一括で約定し、全端末と会場画面が1秒以内の差で新価格を公開する
5. 約定・一部約定・不成立とその理由が本人に表示される
6. 表示価格は毎回整数で合計100Gになり、その価格で約定する
7. 調査券を第3・第4ラウンドのどちらかで1回使える（D-020）
8. 決算では次を表示する
   - ドラゴン輸送の成功証を100Gで精算した結果と順位
   - 最初と最後の本命（D-021）
   - 価格のリプレイ（NPCと参加者の注文を区別する）
9. 再読み込み、画面ロック、回線の切替のあと3秒以内に状態が戻り、注文が重複しない

整合性

10. 締切＋1秒を過ぎた注文が通らない
11. 清算と決算を何度呼んでも、1回分しか反映されない
12. 全勘定の現金合計が一定で、ギルド別の口数合計が0。負の残高や負の保有がない
13. 同じシナリオ版と注文なら、同じ結果ハッシュになる
14. 他の商会の予約や保有が見えない。商会名以外の個人情報を持たない

運用

15. 本番環境で、4G回線を使ったリハーサルを2回完走している
16. ローカル環境への切替と、録画した対戦の上映を含む当日の手順書がある
17. 費用、データ削除の手順、出口が文書にある

## 8. テスト

**エンジン（Vitest）**

- `MARKET_SPEC.md` §7の不変条件
- 境界になる注文：往復売買、4ギルド同時買い、全員が逆張り、全員が同じギルド、売りだけ、参加者0人、残高ぎりぎり
- 清算の性質：減算ループの停止、同じ入力で同じハッシュ、kを変えても基準の値動きが同じ
- シード固定のランダム戦略で1万試合を回し、不変条件の違反が0

**DB統合（ローカルPostgres）**

- 締切直前に6商会が同時に注文する
- 締切と注文の競合（猶予の境界の前後）
- 締切処理を同時に10回送っても清算は1回
- 同じ注文の再送、古い版番号での上書き拒否
- 決算を2回呼ぶ、一時停止中の注文を拒否する
- 処理の途中でプロセスを落としても、部分的な書き込みが残らない

**E2E（Playwright）**

- 参加者6、会場画面、運営の8コンテキストで5ラウンドを完走し、全端末の公開時刻の差を測る
- 再読み込みからの復帰、スリープ相当（ポーリング停止→再開）
- 360px幅で主要な操作が隠れない

**負荷**

- 12商会が1秒ごとに状態を取得し、締切の1秒前に全員が注文する試合を5回続けて流す（会議規模の2倍）

## 9. 当日の運用

会議前：

- 前日と当日の朝に、本番URLで試合を作り、4G回線のスマートフォン2台で1ラウンドを通します（DBの停止やデプロイの不備を見つけるため）。
- リハーサルの対戦を録画しておきます（最後の予備）。
- 会場画面はノートPCからTVへ出します。運営の操作は同じPCか、発表者のスマートフォンで行います。
- ノートPCで、内部テストと同じローカル環境をすぐ起動できるようにしておきます。

当日の障害：

| 症状 | 対応 |
| --- | --- |
| 参加できない端末がある | 隣の人と1台を共有する（D-018と同じ考え方） |
| 一部の端末の表示が古い | ページを再読み込みする（状態はサーバーから戻る） |
| 締切後に進まない | 運営の「早期締切」を押す（冪等）。だめなら一時停止→再開 |
| 清算でエラーが出る | ロールバック済みなので再試行する。続くなら試合を中止し、新しい試合を作る |
| 本番サイトに届かない | ノートPCのローカル環境を起動し、PCのテザリングに参加してもらう |
| どれも使えない | 録画した対戦を上映して説明する |

監視はVercelのログと、運営画面の「接続中の端末数・最後に状態を取得した時刻」だけにします。外部の監視サービスは入れません。

## 10. プレイテストの判定

会議前の内部テスト（5〜6人、LAN）と会議本番で、同じ観察票を使います。内部テストの結果は問題の発見に使い、継続率や教育効果の証明にはしません（`DATA_AND_EVALUATION.md`）。

| 観点 | 見るもの | 目安 |
| --- | --- | --- |
| 理解 | 第1ラウンドの受付開始から最初の予約までの秒数、「なぜこの値段なのか」という質問の数 | 30秒以内。質問が約定の仕組みに集中していないか |
| 興奮 | 公開の瞬間の声や身振り（観察者が記録）、順位表示への反応 | 5ラウンド中3回以上 |
| 戦略の分かれ方 | 第3・第4ラウンドで、逆張り、様子見、調査券の使い方が分かれたか | 全員が同じ行動にならない |
| 再挑戦 | 終了直後の「もう1回」という発言や依頼 | 1人以上 |
| 技術 | 意図しない拒否、公開のずれ、復帰の失敗 | 0件 |

終了後に聞く5問：

1. 何をするゲームか、一言で説明できますか
2. 一番盛り上がった瞬間はどこですか
3. 締切のあとに価格が決まる仕組みは分かりましたか
4. 他の人やNPCの動きを予想して注文しましたか
5. 自行のイベントで子どもに遊ばせたいと思いますか
